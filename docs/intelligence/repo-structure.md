# Repository Structure

This document describes the target monorepo layout for randbats-bot after the Phase 1 restructuring.

---

## Directory Layout

```
randbats-bot/
├── extension/          ← Chrome extension (UI, content script, service worker)
│   ├── inject/         Hook into PS page (PAGE world script)
│   ├── content/        Bridge, protocol tracking, battle session (ISOLATED world)
│   ├── worker/         Service worker message routing
│   ├── ui/             Preact overlay + dev panel (Shadow DOM)
│   └── offscreen/      Offscreen document for eval + ML inference
├── engine/             ← Pure TS: search, eval, damage, opponent model
│   ├── search/         Minimax, ISMCTS, iterative deepening
│   ├── eval/           Heuristic + learned evaluation
│   ├── damage/         @smogon/calc wrapper, @pkmn/engine integration
│   ├── model/          Opponent model, Bayesian narrowing
│   └── sim/            @pkmn/engine WASM integration
├── training/           ← Python: data pipeline + model training
│   ├── scraper/        Replay download + parsing
│   ├── features/       Feature extraction from battle states
│   ├── train/          PyTorch training scripts (value net, policy net)
│   ├── self-play/      Self-play game generation + RL loop
│   └── export/         ONNX export + validation
├── models/             ← Trained model artifacts (.onnx files)
├── data/               ← Static data (randbats sets, replay fixtures)
│   ├── sets/           Randbats set JSONs (from data.pkmn.cc)
│   ├── replays/        Downloaded replay data (gitignored, large)
│   └── fixtures/       Small test fixtures checked into git
├── docs/               ← Architecture, plans, roadmap
│   ├── intelligence/   Implementation plan, research notes
│   └── debugging/      Dev mode, turn logging guides
├── scripts/            ← Build, dev-launch, data pipeline, benchmarks
└── test/               ← Integration tests, replay fixtures, e2e
```

---

## Why Monorepo

| Reason | Explanation |
|--------|-------------|
| **Coordination overhead** | Engine changes often require extension changes (new message types, new eval interface). A single repo means one PR, one review, one merge. |
| **Shared types** | `types.ts` defines `BattleSnapshot`, `ScoredOption`, `OpponentModel` — used by both engine and extension. No version drift. |
| **Atomic changes** | Refactoring the eval interface updates engine + extension + tests in one commit. No cross-repo dependency hell. |
| **Simpler CI** | One pipeline builds everything, runs all tests, catches integration issues immediately. |
| **Developer experience** | `npm install` + `npm run build` gets everything working. No submodule dance. |

## Boundary Rules

### engine/ — Pure computation, no platform dependencies

- ✅ TypeScript, pure functions, classes
- ✅ Imports: `@smogon/calc`, `@pkmn/data`, `@pkmn/engine`, standard lib
- ❌ NO Chrome APIs (`chrome.runtime`, `chrome.storage`, etc.)
- ❌ NO DOM APIs (`document`, `window`, `HTMLElement`)
- ❌ NO Node.js APIs (`fs`, `path`, `process`) — except in test files
- **Testable with**: Vitest, runs in Node.js or browser environment
- **Consumed by**: extension (via import), scripts (via import), tests

### extension/ — Chrome extension, platform-specific

- ✅ Chrome extension APIs, DOM manipulation, Preact components
- ✅ Imports from `engine/` (the engine is a dependency)
- ❌ NO direct imports from `training/`
- ❌ NO Node.js APIs in production code (content scripts run in browser)
- **Built with**: Vite (multi-entry: inject, content, worker, offscreen, ui)
- **Output**: `dist/` folder ready for `chrome://extensions` → Load unpacked

### training/ — Python only, offline pipeline

- ✅ Python 3.10+, PyTorch, numpy, pandas
- ✅ Reads from `data/` and `models/`
- ✅ Writes to `models/` (ONNX artifacts)
- ❌ NO TypeScript, NO npm dependencies
- ❌ NO runtime connection to the extension
- **Environment**: pip/conda, separate `requirements.txt`
- **Runs on**: Developer machine or GPU cloud instance

### models/ — Artifacts only

- Contains `.onnx` files produced by `training/export/`
- Consumed by `extension/offscreen/` at runtime (bundled into extension or fetched)
- Git LFS for files >1MB, or gitignored with download script

### data/ — Static + generated

- `data/sets/` — checked in, small JSON files from data.pkmn.cc
- `data/replays/` — gitignored, generated by `training/scraper/`
- `data/fixtures/` — checked in, small test fixtures for unit tests

## Import Graph

```
extension/ ──imports──→ engine/
scripts/   ──imports──→ engine/
test/      ──imports──→ engine/ + extension/
training/  ──reads────→ data/
training/  ──writes───→ models/
extension/ ──bundles──→ models/
```

No circular dependencies. `engine/` is the leaf — it imports nothing from the project, only external packages.

## Build System

| Component | Tool | Command | Output |
|-----------|------|---------|--------|
| Extension | Vite | `npm run build` | `dist/` (Chrome extension) |
| Engine | TypeScript + Vitest | `npm test` | Tests pass, type-checks |
| Training | pip + Python | `python training/train/value_net.py` | `models/*.onnx` |
| Scripts | tsx | `npx tsx scripts/bench-search.ts` | Console output |

### Vite config (extension build)

Multi-entry build producing separate bundles:
- `inject/hook.ts` → `dist/inject.js` (PAGE world, IIFE)
- `content/bridge.ts` → `dist/content.js` (ISOLATED world)
- `worker/sw.ts` → `dist/sw.js` (service worker)
- `offscreen/ml-eval.ts` → `dist/offscreen.js` (offscreen document)
- `ui/overlay.tsx` → bundled into content script

### TypeScript config

```jsonc
// tsconfig.json (root)
{
  "compilerOptions": {
    "strict": true,
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "paths": {
      "@engine/*": ["./engine/*"],
      "@extension/*": ["./extension/*"]
    }
  }
}
```

## Migration Plan (from current src/)

The current `src/` layout maps to the new structure as follows:

| Current | New | Notes |
|---------|-----|-------|
| `src/eval/minimax.ts` | `engine/search/minimax.ts` | Core search logic |
| `src/eval/scoring.ts` | `engine/eval/heuristic.ts` | Heuristic evaluator |
| `src/eval/damage.ts` | `engine/damage/smogon-calc.ts` | Display-layer damage |
| `src/eval/opponent-model.ts` | `engine/model/opponent-model.ts` | Bayesian narrowing |
| `src/eval/eval-worker.ts` | `extension/offscreen/eval-worker.ts` | Worker entry point |
| `src/inject/hook.ts` | `extension/inject/hook.ts` | PAGE world hook |
| `src/content/bridge.ts` | `extension/content/bridge.ts` | Content script |
| `src/worker/sw.ts` | `extension/worker/sw.ts` | Service worker |
| `src/ui/overlay.tsx` | `extension/ui/overlay.tsx` | Preact overlay |
| `src/ui/suggestion-card.tsx` | `extension/ui/suggestion-card.tsx` | UI component |
| `src/state/snapshot.ts` | `engine/state/snapshot.ts` | State extraction |
| `src/state/sets-db.ts` | `engine/state/sets-db.ts` | Sets data loader |
| `src/types.ts` | `engine/types.ts` + `extension/types.ts` | Split shared vs extension-specific |

**Migration steps**:
1. Create new directory structure
2. Move files with `git mv` (preserves history)
3. Update all import paths
4. Update Vite config entry points
5. Verify build + tests pass
6. Single commit: "refactor: split src/ into engine/ + extension/"

## When to Split

The monorepo should be split into separate repositories **only if**:

1. **Training needs dedicated GPU CI** — If training pipelines need expensive GPU runners that shouldn't block extension CI, split `training/` into its own repo with its own CI pipeline. The interface is just the `.onnx` files it produces.

2. **Engine becomes a standalone package** — If other projects want to use the search/eval engine (e.g., a Discord bot, a CLI tool, a different extension), publish `engine/` as an npm package (`@randbats-bot/engine`). The extension then depends on it like any other package.

3. **Team grows beyond 3-4 people** — If different people own training vs extension and coordination overhead of the monorepo exceeds its benefits.

**Until then**: keep everything together. The simplicity of one repo, one `npm install`, one CI pipeline outweighs the theoretical cleanliness of separate repos.
